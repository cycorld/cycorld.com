101개 엔드포인트를 다시 짜며 배운 것: Django vs Rust, 그리고 AI 코딩의 진짜 비용

2026-08-25

"AI가 코드를 다 짜주는 시대인데, 개발 속도가 빠른 파이썬을 두고 굳이 러스트(Rust)를 쓸 이유가 있을까?"

실제 운영 중이던 위치 기반 소셜 백엔드(101개 엔드포인트 규모)를 Django에서 Rust(Axum + SQLx)로 완전히 다시 작성하면서 내가 스스로에게 던졌던 질문이다.

흔히들 AI 시대에는 빠른 프로토타이핑이 생명이니 동적 언어가 유리하다고 말한다. 러스트는 엄격한 컴파일러 규칙 때문에 AI가 토큰만 낭비할 것이라는 걱정도 많았다. 하지만 101개 엔드포인트를 전부 AI 에이전트로 포팅하고 수개월간 실제 서버를 돌려본 결과, 우리가 흔히 생각하는 ‘AI 개발의 효율성’과 ‘운영 비용’의 계산법은 완전히 뒤집어졌다.

현장에서 직접 측정한 데이터와 함께 그 이유를 담백하게 정리해본다.

1. 코드량 실측: 176개 파일의 분산 vs 51개 파일의 응집

기존 Django 백엔드와 새로 작성한 Rust 백엔드는 완전히 같은 기능(PostGIS 기반 위치 쿼리, JWT 인증, 푸시 알림, 결제/포인트 등 101개 API)을 수행한다. 두 코드베이스의 물리적 수치는 이렇다.

항목Django (DRF)Rust (Axum + SQLx)차이와 특징
소스 파일 수176개 (.py)51개 (.rs)Rust가 71% 적음 (도메인 응집)
전체 소스 라인 (LOC)11,856 라인12,380 라인전체 라인 규모는 유사 (+4%)
실제 실행 코드 (Code)9,618 라인10,158 라인Rust가 약 5% 많음
순수 비즈니스 로직약 6,200 라인약 10,158 라인Rust가 1.6배 더 긺 (명시적)
파일당 평균 라인 수약 67 라인 (파편화)약 243 라인 (단일 완결)구조적 차이 뚜렷

숫자가 흥미롭다.

Django는 ORM과 Serializer의 메타프로그래밍 덕분에 비즈니스 로직 자체는 6,200라인으로 짧다. 하지만 코드가 models/, views/, serializers/, services/, middlewares/, urls.py로 잘게 쪼개져 176개 파일에 흩어져 있었다.

반면 Rust는 요청/응답 구조체, SQL 쿼리, 에러 처리를 전부 명시적으로 써야 해서 코드가 1만 라인으로 늘어났다. 대신 라우트 파일 하나에 입출력과 쿼리를 모두 모아두어 파일 수는 51개로 줄었다.

이 파일 구조의 차이가 AI 코딩에서 결정적인 차이를 만들었다.

2. 개발 비용: 토큰은 러스트가 40% 더 썼다

AI 에이전트를 통해 101개 엔드포인트를 구현할 때 소모된 예상 토큰량을 단계별로 비교해보면 이렇다.

개발 단계Django (Python)Rust비고
1. 기본 세팅 및 인증 구조약 250만 토큰약 350만 토큰Rust의 타입 정의 및 초기 보일러플레이트
2. 101개 엔드포인트 구현약 2,200만 토큰약 3,300만 토큰엔드포인트당 Rust가 1~2턴 더 소요
3. 테스트 및 정합성 검증약 1,200만 토큰약 1,500만 토큰컴파일 검증 vs 런타임 디버깅
4. 배포 및 인프라 스크립트약 150만 토큰약 250만 토큰크로스 컴파일 및 바이너리 패키징
총 토큰 소모량약 3,800만 토큰약 5,400만 토큰Rust가 약 42% 더 소모
순수 AI API 비용 (추정)약 16만 원 ($120)약 27만 원 ($200)Sonnet/Opus 혼합 기준

러스트가 토큰을 약 40% 더 썼다. 이유는 두 가지다.

  1. 긴 텍스트 덩어리: 타입 정의와 SQL 쿼리가 명시적이라 AI가 읽고 쓰는 코드 블록 자체가 크다.
  2. 컴파일러와의 줄다리기: cargo check와 소유권 규칙을 통과하기 위해 AI가 수정 ➔ 에러 확인 ➔ 재수정하는 턴이 엔드포인트당 1~2회 더 발생했다.

단순히 초기 개발 토큰 비용만 보면 파이썬의 판정승이다. 하지만 이야기는 여기서 끝나지 않는다.

3. 왜 AI는 러스트에서 덜 헤맸을까?

파이썬이 토큰을 적게 쓴 것은 사실이지만, AI가 파이썬 코드를 짤 때 훨씬 자주 ‘침묵의 버그’를 만들었다. 문법은 맞는데 런타임에 NoneType 에러가 나거나, Serializer 필드가 슬그머니 누락되는 식이다. AI에게는 자기가 짠 코드가 맞는지 즉시 알려주는 ‘오라클’이 없었다.

반면 러스트는 달랐다. 컴파일러가 가장 저렴하고 정확한 채점관 역할을 해줬다.

여기에 더해, 우리는 라우트 파일 하나에 DTO와 SQL 쿼리를 한 번에 담는 평탄한 수직 슬라이스(Vertical Slice) 아키텍처를 썼다. AI는 계층을 넘나들며 5개 파일을 뒤적거릴 필요 없이, 단 1개 파일 안에서 맥락을 끝낼 수 있었다.

(※ AI가 왜 복잡한 계층 구조보다 평탄한 아키텍처에서 압도적으로 높은 성공률을 보이는지는 학술 연구 리뷰: AI 에이전트는 왜 클린 아키텍처를 싫어할까 글에 연구 배경을 정리해두었다.)

4. 운영 비용(TCO)의 반전: 2주 만에 뒤집힌 계산서

진짜 승부는 개발이 끝나고 서버를 올린 뒤에 시작되었다. 매달 나가는 클라우드 인프라 비용과 유지보수 품을 계산해보니 결과는 완전히 반대였다.

비용 항목Django (Gunicorn 8 Workers)Rust (Axum 단일 프로세스)
서버 사양 (AWS EC2)t4g.xlarge (월 13만 원)t4g.micro (월 2만 원)
메모리 점유율 (RSS)1.6 GB ~ 2.0 GB20 MB ~ 40 MB (98% 감소)
P99 응답 속도50ms ~ 200ms1ms ~ 5ms
Sentry 500 에러월 수만 건 (키 누락, 타입 에러)0건에 수렴
유지보수 AI 토큰사이드이펙트 추적으로 지속 소모타입 에러 지점만 즉시 수정
 
[연간 총 운영 비용(TCO) 추정]
- Django : 서버비(160만 원) + 에러 대응(80만 원) + 유지보수 토큰(50만 원) = 약 290만 원
- Rust   : 서버비(24만 원) + 에러 대응(0만 원) + 유지보수 토큰(20만 원) = 약 44만 원
────────────────────────────────────────────────────────────────────────
➔ 1년에 약 246만 원 절감 (초기 개발에서 더 쓴 토큰값 11만 원은 2주 만에 회수)

Django를 쓸 때는 N+1 쿼리와 워커당 200MB씩 먹는 메모리 때문에 인스턴스를 줄일 수 없었다. 반면 Rust는 동시 요청이 몰려도 메모리를 30MB밖에 쓰지 않았고, 알 수 없는 500 에러가 사실상 사라졌다.

5. 현장의 결론

  1. 초기 개발비는 빙산의 일각이다.
    AI 덕분에 러스트의 진입 장벽이 낮아졌다. 초기에 토큰을 40% 더 쓰더라도, 운영 단계에서 얻는 인프라 절감과 무장애 안정성이 그 비용을 몇 배로 보상한다.
  2. AI 시대의 아키텍처는 ‘평탄함’이다.
    코드가 짧은 것보다 중요한 것은 한 파일 안에 기능이 완결되어 AI의 시야(Context)를 흩뜨리지 않는 것이다.

앞으로 새로운 백엔드를 만든다면, 나는 주저 없이 "평탄한 아키텍처 위에 올린 정적 타입 언어"를 고를 것이다. 그것이 AI와 사람 모두에게 가장 경제적이기 때문이다.
